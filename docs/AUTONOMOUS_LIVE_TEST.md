# Полный живой тест без Safari

Последний результат: [полный протокол 17.10.2026](LIVE_FULL_RESULT_2026-10-17.md).

## Запуск

Из корня проекта:

```bash
bash scripts/test_live_full.sh --label vpn-on
```

После отключения VPN для контрольного сравнения:

```bash
bash scripts/test_live_full.sh --label vpn-off
```

Сценарий сам собирает браузерный образ, создаёт новый отдельный профиль Chromium,
проверяет все 70 исходных фраз с глубиной 200 и сохраняет настоящие ответы через
обычный `Collector` в рабочую SQLite. Повторная проверка тех же страниц использует
память текущего запуска и не удваивает HTTP-трафик. Рабочая история не очищается.
Тестовые карточки в рабочую историю не добавляются. Safari может быть закрыт.

Состояние VPN указывается оператором через метку, автоматически не определяется
и не переключается. Если worker уже работает, сценарий попросит сначала выполнить
`docker compose stop collector`, чтобы не создавать параллельную нагрузку на WB.

Для короткой предварительной проверки одной фразы:

```bash
bash scripts/test_live_full.sh --label single --query 'постельное белье 2 спальное'
```

Проверенный в браузерных запросах регион — `dest=1259570991`, RUB, popular.
`--dest CODE` задаёт другой регион; при уже накопленной успешной истории защита
SQLite запрещает подменять её регион. Точное соответствие кода нужному адресу
доставки следует проверить отдельно.

## Отчёты

Для каждого запуска создаётся отдельная папка `data/live-tests/<UTC-time>-<label>-<pid>/`:

- `console.log`: ход выполнения;
- `results.jsonl`: каждая фраза, 200 ID по порядку для полных выдач, характеристики,
  число запросов и повторов, ID соответствующего снимка в SQLite;
- `summary.json`: сколько фраз выполнено, сколько прошло, сколько осталось,
  причина остановки и число обновлений браузерной сессии.

Код завершения `0` означает полный top-200 для каждой проверяемой фразы.
Код `2` означает неполную выдачу, ошибку данных или блокировку. При отказе WB
оставшиеся фразы не запрашиваются и явно учитываются в `not_run`.

Неполные данные не выдаются за полный top-200. Если WB возвращает меньше товаров,
сценарий сохраняет частичный статус. Валидное поле `total` позволяет остановиться
на подтверждённом конце выдачи, например после страниц 100 + 14 при `total=114`. При дублировании артикула между страницами
весь снимок повторяется один раз; дубли не удаляются со сдвигом позиций. Если
повтор тоже некорректен, результат остаётся ошибкой. При сохранении в БД обе
реальные попытки остаются в журнале.

## Как работает самостоятельная сессия

Отдельная конфигурация `compose.browser.yaml` запускает SeleniumBase CDP и Chromium
с виртуальным экраном внутри Docker. Браузер загружает обычный сайт, затем обычную
страницу поиска. Адаптер проверяет фактический HTTP 200 с товарным JSON и берёт
актуальные заголовки и параметры из этого запроса. Токен, TLS и запросы данных
остаются внутри того же браузера. Личные браузерные профили не используются.

Запросы выдерживают паузу минимум 5 секунд после завершения предыдущего запроса;
между фразами — ещё 5 секунд. До трёх попыток при временных HTTP/сетевых сбоях,
нарастающая пауза с учётом `Retry-After`. При 498 допускается одна ограниченная
попытка восстановить сессию обычной загрузкой страницы поиска. CAPTCHA не решается.

Браузерный runtime устанавливается только в отдельном Docker target `browser`.
Обычный образ панели не получает зависимости SeleniumBase. Профили хранятся в
томе Docker с правами 0700; cookies не попадают в отчёты или исходники.

## Постоянный запуск платформы

После проверки:

```bash
docker compose -f compose.yaml -f compose.browser.yaml up -d --build
docker compose -f compose.yaml -f compose.browser.yaml logs -f collector
```

Панель: `http://127.0.0.1:8501`. История собирается с текущего момента, без
создания записей за прошлые часы. Диагностические снимки — настоящие попытки
сбора и потому могут отображаться в панели.
